# notion-archive

규칙판 2026-10-09 · 정본은 이 파일이다. 노션 공통 규칙 페이지와 쓰는 법이 다르면 이 파일을 따르고, 다른 점을 보고에 한 줄 적는다.

읽는 사람은 맥락을 다 잊은 나중의 나다. 목표는 그 사람이 페이지를 **빨리 읽고 이해하는 것**이다.
모든 규칙은 한 기준으로 판단한다. **읽는 비용과 짐작하는 비용을 합친 총비용이 줄어드는가.** 형식을 맞추는 것은 목적이 아니다.

```
- [ ] 1. 저장 위치·스키마 확인, 같은 목적의 글 찾기 (2절)
- [ ] 2. 첫 화면부터 쓰기: 결론 상자 → 맥락 줄 → 용어 줄 → 할 일 (3절)
- [ ] 3. 본문 블록마다 질문을 보고 모양 고르기 (4·5절)
- [ ] 4. 문장 다듬기, 근거 표시 (6·7절)
- [ ] 5. 아래쪽 정리: 확인용 접기, 조사 원자료 (8절)
- [ ] 6. 속성 채우기 (11절) → 저장 전 점검 5개 (12절)
- [ ] 7. 저장 → 다시 열어 확인 → 보고 (13절)
```

노션 문법은 [references/notion-format.md](references/notion-format.md), 블록 모양별 예시는 [references/examples.md](references/examples.md)에 있다. 예시와 이 파일이 다르면 이 파일을 따른다.

## 1. 이 스킬을 쓰지 않는 경우

- "내 차는 아반떼야, 기억해"처럼 나에 관한 사실을 남기는 요청은 이 스킬이 아니다. 지금 환경의 메모리 기능(노션 메모리, ChatGPT 메모리 등)에 맡긴다.
- 내용이 링크 하나나 두 줄이라 결론이 서지 않으면 한 번 묻는다. "기존 글에 붙일까, 짧은 클리핑으로 둘까?"

## 2. 어디에 저장하고, 새로 쓸지 고칠지

**위치**
1. 사용자가 지정한 곳이 있으면 거기에 저장한다.
2. 지정이 없으면 원본 DB에 저장한다. 부모는 `data_source_id: c61e2921-0d06-4a02-a7af-75e9ba4d2858`로 지정한다. 이름으로 찾지 않는다.
3. `📚 ChatGPT 아카이브`는 열람용 홈 페이지다. 그 밑에 만든 하위 페이지는 아카이브 저장이 아니다.
4. 접근·권한 오류가 나면 실패한 단계를 알리고 멈춘다. 동의 없이 다른 곳에 저장하지 않는다.

**같은 목적의 글 찾기**
- `출처 URL`이 같은 글, 제목·키워드가 겹치는 글을 찾는다. 제목만 보고 판단하지 않는다. 후보를 열어 읽는다.
- 대상과 목적이 같으면 새로 만들지 않고 그 글을 고친다(10절). 애매할 때만 한 번 묻는다.
- 날짜가 다른 독립된 사건은 비슷해 보여도 합치지 않는다.
- 사용자가 새 글을 원하면 새로 만든다.

**목적 하나에 페이지 하나**
- 결론이 4개 이상 필요하면 목적이 둘이다. 페이지를 나누고 서로 `<mention-page>`로 잇는다.
- 한 목적을 여러 장으로 쪼개지 않는다.

원본 대화는 저장하지 않는다. 그래서 결정적인 수치·인용·조문은 원문 표현 그대로 옮기고 출처를 붙인다.

## 3. 첫 화면 — 모든 글이 같은 모양

순서는 고정이다. **결론 상자 → 맥락 줄 → 용어 줄 → 할 일 목록.** 맥락·용어·할 일은 필요할 때만 둔다.

### 결론 상자

결론은 1~3개를 번호로 쓴다. 결론 하나는 아래 칸 가운데 필요한 것만으로 짓는다. 칸 하나가 문장 하나다. 순서는 표의 순서를 따른다.

| 칸 | 답하는 질문 | 넣는 때 |
| :--- | :--- | :--- |
| 판단 | 무엇이 결론인가 | 항상. 판단만으로 뜻이 서지 않으면 풀어 주는 문장 하나를 붙인다 |
| 조건 | 무엇이 바뀌면 결론이 뒤집히나 | 빼면 결론이 과장되거나 틀려질 때 |
| 근거 강도 | 얼마나 믿을 만한가 | 근거가 경험담·추정이거나 자료끼리 다를 때 |
| 행동 | 누가 무엇을 언제 하나 | 할 일이 있을 때 |

**판단 문장은 글의 성격에 맞는 형태로 쓴다.** 고를 것이 있는 글은 누가 정했는지 드러낸다.

| 글의 성격 | 판단 문장 형태 |
| :--- | :--- |
| 고르는 글 — 사용자가 정함 | "○○로 정했다." 사용자가 대화에서 직접 정했다고 말했을 때만 |
| 고르는 글 — AI가 제안, 사용자 미확정 | "○○를 추천한다. 아직 정하지 않았다." |
| 고르는 글 — 결론이 아직 없음 | "아직 결론이 없다. 남은 질문은 ○○다." |
| 알게 된 것을 정리한 글(개념·조사·문서 요약) | 알게 된 사실을 평서문 한 문장으로. "PREP와 BLUF는 경쟁 기법이 아니다." |
| 모은 글(목록·클리핑) | "○○에 관한 △△ N개를 모았다." |

**결론을 쓴 뒤 네 가지를 본다.**
1. 첫 문장만 읽어도 결론을 알 수 있는가.
2. 이 문장을 지우면 결론이 과장되는가. 그렇다면 남기고, 아니면 본문으로 내린다.
3. 한 문장에 판단이 둘이면 쪼갠다.
4. 결론 자리에 배경이나 경위가 오면 본문으로 보낸다.

- 할 일이 하나면 행동 칸에 쓴다. 둘 이상이면 가장 먼저 할 것만 행동 칸에 쓰고, 전체는 할 일 목록에 둔다.
- 함정은 상자를 따로 만들지 않는다. "주의:"로 시작하는 문장을 그 함정이 걸린 행동 바로 앞에 둔다. 결론 전체를 뒤집는 함정이면 조건 칸에 쓴다.
- 결론을 막는 미확인 사항은 조건 칸에 쓴다. `○○는 확인하지 못했다. ○○이면 결론이 바뀐다.`
- 본문을 쓰다 결론에 조건이 붙으면 결론 상자 자체를 고친다. 본문 끝에서 결론을 되풀이하지 않는다.

### 맥락 줄 (회색 한 줄)

`누가 ○○ · 왜 ○○ · 출처 ○○ · 기준일 YYYY-MM-DD · 보강 YYYY-MM-DD` 가운데 이 페이지에 의미 있는 것만 쓴다. 이름표는 이 다섯 가지와 `결론 변경`만 쓴다.
- 가격·제도·법령·시세처럼 시간이 지나면 틀릴 수 있는 내용이면 기준일을 반드시 넣는다. 기준일은 정보가 언제 시점인지다. 할 일의 기한과 다르다.
- 모르는 항목은 쓰지 않는다.

### 용어 줄 (회색 한 줄)

첫 화면에 나온 낯선 용어만 한 구절씩 푼다. `용어: STE100 = 기술문서의 단어·문장을 제한한 국제 영어 표준`
- 낯선지는 "이 분야를 모르고 맥락도 잊은 나"를 기준으로 판단한다.
- 결론 문장 안에서는 용어를 풀지 않는다. 결론이 길어지고 흐려진다.

### 할 일 목록

할 일이 둘 이상일 때만 둔다. 체크박스 한 줄에 할 일 하나, 시점을 붙인다. 날짜가 없으면 계기로 쓴다(`계약 전`, `첫 사용 전`).

## 4. 본문 — 블록마다 "답하는 질문"으로 모양을 고른다

본문은 덩어리(블록)로 나눈다. 블록마다 그 블록이 답하는 질문을 보고 모양을 고른다. 한 페이지에 여러 모양이 섞여도 된다. 한 블록이 질문 둘에 답하면 블록을 나눈다.

| 블록이 답하는 질문 | 모양 |
| :--- | :--- |
| 왜 그런가? | 소결론 → 이유 → 근거. 근거 자료가 없으면 근거를 비우고 이유만 쓴다. 이유 여러 개가 서로 경쟁하면 "뭘 고르나?" 모양으로 바꾼다 |
| 어떻게 하나? | 번호 단계. 한 줄에 행동 하나. 조건을 행동보다 먼저 쓴다. "주의:" 문장은 그 주의가 걸린 단계 바로 앞에 둔다 |
| 무엇인가? | 뜻 → 작동 원리 → 예시 → 흔한 오해 |
| 뭘 고르나? | 판단 기준을 먼저 쓰고, 비교표를 둔다. 표 바로 위에 그 표의 결론을 한 줄 쓴다 |
| 어떻게 흘러갔나? | 시간순 목록. 시점 + 일어난 일 |
| 어떻게 연결되나? | 그림(5절) |
| 얼마인가? | 계산 표. 값 + 식 + 전제 |

- **소제목은 그 블록의 결론으로 쓴다.** 소제목만 이어 읽어도 페이지의 논리가 보여야 한다. `연결 방법` ❌ / `연결 — 맥미니 뒤쪽 포트에 바로 꽂는다` ⭕
- **순서는 결정에 영향이 큰 블록부터 놓는다.** 배경과 경위는 뒤로 보낸다.
- 블록 개수에는 상한을 두지 않는다. 분량은 "결론이 4개 이상이면 페이지를 나눈다"가 막는다.
- 본문에서 처음 나오는 어려운 말은 그 자리에서 쉬운 말로 한 번 풀고 원어를 괄호에 둔다. 첫 화면 용어 줄에서 이미 푼 말은 다시 풀지 않는다.
- 비교표는 3~4열까지 쓴다. 행마다 출처가 다르면 `출처` 열을 둔다.

## 5. 그림 — 글로 쓰면 머릿속에서 조립해야 할 때만

- 넣는 기준: 요소가 3개 이상이고 서로 연결되거나 갈라진다. 목록이나 표로 충분하면 넣지 않는다. 꾸미는 그림은 넣지 않는다.
- 도구는 가벼운 것부터 고른다.
  1. 표: 비교, 조회.
  2. 머메이드 흐름도: 흐름, 구조, 분기, 계층.
  3. HTML 임베드: 단계별로 펼쳐 보는 설명이나 값을 바꿔 보는 계산처럼 머메이드로 안 되는 이해용 시각화. 첨부 파일을 만드는 노션 도구가 있을 때만 쓴다. 없으면 머메이드로 대신한다.
  4. 이미지: 위 셋으로 안 될 때만.
- 그림 바로 아래에 회색 한 줄로 이 그림이 보여 주는 것을 쓴다.

## 6. 문장 — 해석할 여지를 없앤다

**모든 블록 공통**
- 본문 문장은 "~다"로 끝낸다. "확인 필요", "설치 완료" 같은 명사형 끝맺음은 쓰지 않는다. 표 칸과 라벨만 예외다.
- 한 문장에는 판단 하나 또는 행동 하나만 담는다. 글자 수가 아니라 이 기준으로 끊는다.
- 한 대상은 한 이름으로만 부른다. 앞에서 "외장 SSD"라고 했으면 끝까지 "외장 SSD"다. 다른 이름은 `키워드` 속성으로 보낸다.
- 기준 없는 말을 쓰지 않는다: 적절히, 충분히, 필요시, 약간, 등. 기준이 있으면 기준을 쓰고, 없으면 지운다.
- 대상을 가리키는 말 대신 이름을 쓴다: 이것, 그것, 해당 ○○ → 실제 이름.
- 수치에는 단위를 붙인다. 범위가 있으면 범위를 쓴다.

**블록 목적에 따라 엄격함을 다르게 한다**

| 엄격함 | 적용 블록 | 더하는 규칙 |
| :--- | :--- | :--- |
| 최고 | 행동을 지시하는 블록: 절차, 주의, 할 일 | 조건 → 행동 순서. 책임자가 중요하면 행위자를 쓴다. 좌우·반복 작업은 각각 쓴다("반대쪽도 동일" 금지). 이중부정 금지 |
| 중간 | 판단·설명·비교 블록 | 공통 규칙만 |
| 낮음 | 쉬운 설명과 비유 | 구어체 허용. 용어 이름은 다른 블록과 같게 쓴다 |

## 7. 근거 — 평소엔 표시하지 않고, 예외만 정해진 말투로

**기본값: 표시가 없는 문장은 확인된 자료에서 온 것이다.** 대부분의 문장은 그냥 쓴다. 잘못 믿으면 판단이 틀어지는 다섯 경우에만 정해진 말투를 쓴다. 한 경우에는 늘 같은 말투만 쓴다.

| 예외 | 정해진 말투 |
| :--- | :--- |
| 개인 경험·후기 | 블록 첫 줄에 "아래는 ○○의 경험이다." 문장은 "~했다고 한다" |
| 비유·설명용 예시 | "비유하면", "설명용 예시로" |
| 확인 못 한 것 | "○○는 확인하지 못했다." |
| 자료끼리 다른 것 | "자료가 서로 다르다: A는 ○, B는 △." |
| 직접 계산한 값 | 값 뒤 괄호에 식. `535,000원 (1,049,000 − 514,000)` |

- "알려져 있다", "~라고 한다(출처 없이)", "일반적으로"는 쓰지 않는다. 출처를 찾았으면 그대로 쓰고, 못 찾았으면 "확인하지 못했다"로 쓴다.
- 어디까지 찾아봤는지, 출처 링크는 본문에 두지 않는다. 아래쪽 `출처` 접기에 둔다.
- 원저자의 주장과 정리하면서 덧붙인 설명을 구분한다. 덧붙인 비유·예시는 위 말투로 표시한다. 원저자 자신의 추정은 "○○ 자체의 추정치다"로 밝힌다.

**지어내지 않는다.** 그럴듯한 숫자 하나가 영구 기록이 되는 것이 이 스킬의 가장 치명적인 실패다.
1. 근거 자료가 대화나 원문에 없으면 근거 자리를 비우고 이유만 쓴다. 사례나 숫자를 만들지 않는다.
2. 가정에 기댄 추정값은 "○○로 가정하면 △△다" 같은 조건문으로만 쓴다.
3. 제도·법령의 시행일과 조항은 공식 원문(국가법령정보센터 등)을 확인한 뒤 쓴다. 확인하지 못하면 "확인하지 못했다"로 남긴다.
4. 원문의 범위를 넓히지 않는다. 원문이 "전신 표준의 실험"이라고 했으면 "현행 표준의 실험"으로 쓰지 않는다.

## 8. 페이지 아래쪽 — 확인용과 원자료를 나눈다

본문 다음에는 다시 열었을 때 던질 질문별로 접기를 둔다. 필요한 것만 둔다.

| 접기 | 내용 |
| :--- | :--- |
| `고르지 않은 이유` | 후보 이름 · 탈락 이유 한 줄 · 그 후보가 이기는 조건. 탈락 후보와 반론을 여기에 합친다 |
| `계산` | 결론에 쓴 숫자의 식과 전제 |
| `이전 결론` | 결론이 바뀌었을 때. 날짜 · 이전 결론 · 바꾼 이유 |
| `원문 위치` | 긴 문서일 때. `원문 2장 PREP → 이 페이지 2번 블록` |
| `출처` | `[제목](URL) — 발행처(날짜)`. 확인 못 한 것은 어디까지 찾았는지 함께 쓴다 |

맨 아래에는 `조사 원자료` 접기 하나를 둔다. 사양 상세, 후기 원문, 링크 묶음, 원본 파일을 넣는다.
- 판단 기준: "나중에 결론을 다시 확인할 때 이걸 열어 볼까?" 그렇다면 확인용 접기, 아니면 원자료다.
- 원자료가 문서 몇 개 분량이면 이 페이지의 하위 페이지로 둔다.
- 원자료는 첨부 파일보다 페이지 글자로 둔다. 첨부 파일 내용은 노션 검색에 걸리지 않을 수 있다.

## 9. 긴 외부 문서를 정리할 때

- 원문의 결론을 첫 화면 규칙대로 놓는다.
- 본문은 원문의 장 순서가 아니라 독자가 던질 질문 순서로 다시 짠다.
- 원문의 장 위치는 `원문 위치` 접기에 색인으로 남긴다.
- 원저자의 주장과 덧붙인 설명은 7절 말투로 구분한다.

## 10. 기존 페이지를 고칠 때

- **판단이 그대로면** 맥락 줄에 `보강 YYYY-MM-DD`를 쓴다.
- **판단이 바뀌면** 맥락 줄에 `결론 변경 YYYY-MM-DD — 이전: ○○`를 쓴다. 이전 결론과 바꾼 이유는 `이전 결론` 접기로 옮긴다. 지우지 않는다.
- 기존의 사실·수치·조건·출처를 지우지 않는다.
- **옛 형식의 글**은 손대는 블록만 새 규칙으로 쓴다. 결론이 바뀌는 갱신일 때만 첫 화면 전체를 새 형식으로 바꾼다. 나머지는 그대로 둔다.
- 고칠 때는 찾아 바꾸기로 필요한 부분만 바꾼다. 본문 전체 교체는 하위 페이지를 지울 수 있어 쓰지 않는다.

## 11. 속성 — 기본 아카이브 DB

저장 전에 원본 DB의 현재 스키마를 읽는다. 스키마에 없는 속성은 넣지 않고 보고에 한 줄 적는다.

| 속성 | 값 |
| :--- | :--- |
| `제목` | 검색될 주제 + 이 페이지만의 구분점. 결론은 넣지 않는다(결론은 `결론` 속성이 보여 준다). 검색될 명사를 앞에 둔다. `맥미니 M6 모니터 고르기` |
| `결론` | 스키마에 `결론`이 있으면 거기에, 아직 `한 줄 결론`이면 거기에 쓴다. 결론 상자에서 판단이나 행동을 바꾸는 결론만 옮긴다. 판단을 맨 앞에, 한 문장에 판단 하나, 1~3문장. 비우지 않는다 |
| `주제 태그` | 업무·행정 / 법령·판례 / 투자·경제 / 여행 / AI·도구 / 학습·개념 / 생활·소비 / 건강 / 기타 / 시스템 **중에서만.** 책장 대응: AI·도구 / 집·생활(생활·소비·건강·투자·경제) / 여행 / 업무(업무·행정·법령·판례). 책장에 띄우려고 맞지 않는 태그를 붙이지 않는다. `시스템`은 운영 규칙·홈·가이드에만 쓴다 |
| `키워드` | 나중에 검색창에 칠 말 5~15개. 본문에 쓰지 않은 다른 이름(동의어·영문·약어)을 반드시 넣는다 |
| `출처 URL` | 대표 출처 하나. 공식 원문이 있으면 그것 |
| `정리일` | 저장하거나 고친 날. 날짜만 |
| `정리 상태` | 새 글은 `수집`. 사용자가 `활용`·`보관`을 말하면 그 값. 고칠 때는 기존 값을 유지한다 |
| `연결 프로젝트` | 진행 중인 프로젝트에 명백히 속할 때만. 애매하면 비운다. 프로젝트 카드를 새로 만들지 않는다 |
| `책장 표지` | 쓰지 않는다 |
| `저장 시각`·`선택` | 건드리지 않는다 |

- 페이지 아이콘은 내용을 대표하는 이모지 하나.
- 다른 DB에 저장하면 그 DB 스키마에 맞춘다. 빈칸을 억지로 채우지 않는다.
- DB가 아닌 일반 페이지로 저장하면 맥락 줄 끝에 `키워드: ○○, △△`를 붙인다.

## 12. 저장 전 점검 5개

예/아니오로 갈리는 것만 본다. 하나라도 걸리면 고친 뒤 저장한다.

1. 결론이 3개 이하이고, 각 결론의 판단 문장이 3절의 다섯 형태 가운데 하나인가.
2. 기준 없는 말(적절히·충분히·필요시·약간·등)과 가리키는 말(이것·그것·해당)이 남아 있지 않은가.
3. 수치마다 단위가 있고, 직접 계산한 값에 식이 붙어 있는가.
4. 같은 대상을 두 이름으로 부르지 않았는가.
5. 원문에 없는 숫자·이름·인과 주장이 없는가. 원문의 범위를 넓힌 표현이 없는가.

## 13. 저장 후 확인과 보고

**다시 열어 확인한다.**
- 부모가 의도한 위치인가. 기본 저장이면 `parent-data-source`가 `c61e2921…`인지 이름이 아니라 ID로 본다.
- 본문이 마지막 접기까지 들어갔는가. `(http://`로 시작하는 뜻밖의 링크가 생기지 않았는가.
- `결론`·`주제 태그`·`정리일`·`정리 상태`·`키워드`가 채워졌는가.
- 저장 응답이 모호하거나 다시 열기가 실패하면 같은 글을 다시 만들지 않는다. 제목으로 먼저 찾는다. 못 찾으면 "저장 응답 성공 / 최종 확인 실패"로 보고한다.

**보고는 이 형태로 짧게 한다.** 본문을 채팅에 다시 늘어놓지 않는다.

```
저장했어 (새 글 | 고침: 보강 | 고침: 결론 변경) → [제목](링크)
결론: (결론 상자의 결론 원문)
확인 못 한 것: (결론에 영향이 큰 것 한두 개. 없으면 이 줄 생략)
대신한 것: (예: HTML 대신 머메이드. 없으면 생략)
규칙판 2026-10-09
```

## 14. 환경별 차이

이 스킬은 Claude(웹·데스크톱·모바일·Claude Code), ChatGPT, Codex에서 같은 파일로 쓴다. 코드 실행은 필요 없다.

- 노션 도구 이름은 환경마다 다를 수 있다. 하는 일로 찾는다: 조회(fetch·search), 만들기(create-pages), 고치기(update-page), 첨부 만들기(create-attachment).
- 첨부 만들기 도구가 없으면 HTML 임베드 대신 머메이드를 쓰고, 보고의 `대신한 것`에 적는다.
- **노션 도구가 아예 연결돼 있지 않으면** 저장하지 않는다. 다른 곳에 대신 저장하지도 않는다. 대신 아래를 준다.
  1. 노션이 연결돼 있지 않아 저장하지 못했다는 한 줄.
  2. 이 규칙대로 쓴 페이지 원고 전체를 코드 블록 하나에. 노션에 붙여넣을 수 있도록 표준 마크다운으로 쓴다. 결론 상자는 인용 블록(`>`)으로, 접기는 일반 소제목으로 바꾼다.
  3. 속성 값 목록: 제목, 결론, 주제 태그, 키워드, 출처 URL.
  4. 붙여넣은 뒤 결론 상자를 콜아웃으로, 아래쪽 소제목을 접기로 바꾸면 된다는 안내 한 줄.
- 규칙판이 다른 사본을 보면 최신 판으로 맞춘다. 사본은 claude.ai 스킬, ChatGPT 스킬, Codex(`~/.agents/skills`), 기기별 Claude Code(`~/.claude/skills`)에 있다.
